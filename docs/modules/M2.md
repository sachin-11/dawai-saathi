# M2 — WhatsApp webhook (inbound)

## Is module me kya banaya
Meta (WhatsApp Cloud API) ke liye ek public endpoint `/webhook/whatsapp`: `GET` se Meta apna subscription verify karta hai, `POST` se har naya message ya status aata hai. Hum signature verify karte hain, payload ko apne `InboundMessage` type me normalise karte hain, user find-or-create karte hain (phone hash + encrypted), message `messages` table me save karte hain, aur BullMQ ke `inbound` queue me job daalkar turant 200 de dete hain. Worker abhi sirf stub hai (job log karke complete). Reply bhejna, media download, consent flow aur AI is module me nahi hai.

## Kyun zaroori tha
Sab kuch isi pe tika hai: agar message miss hua, do baar process hua, ya kisi ne fake request bhej di, to poora bot galat hoga. Meta ka rule hai ki jawab jaldi (kuch second me) aur 200 ke saath do, warna wo wahi message baar-baar bhejta hai. Isliye webhook ko halka rakha (sirf save + enqueue) aur bhaari kaam queue me.

## Kaise kaam karta hai
```
Meta ──GET  /webhook/whatsapp?hub.mode&hub.verify_token&hub.challenge──► token match? ─► challenge (text) / 403
Meta ──POST /webhook/whatsapp  (X-Hub-Signature-256: sha256=...)
          │
          ▼  ThrottlerGuard (300/min)   ─► WhatsAppSignatureGuard (HMAC of RAW body)  ─► 401 if bad
          ▼  parseWebhook()  (zod; messages[] / statuses[] / foreign phone_number_id)
          ▼  har message ke liye:
               UsersService.findOrCreateByPhone   (hash lookup, upsert)
               MessagesService.saveInbound        (INSERT ... ON CONFLICT (wa_message_id) DO NOTHING)
               InboundQueue.add                   (jobId = waMessageId)
          ▼  200 {"status":"received"}              (DB/Redis fail ─► 500 ─► Meta retry karega)

BullMQ "inbound" ──► InboundWorker (stub: ids log karta hai, complete)
```
1. **GET vs POST:** GET sirf ek baar hota hai jab dashboard me webhook set karte ho (handshake). POST har event pe aata hai.
2. **Statuses vs messages:** `messages[]` user ne bheje (hum process karte hain). `statuses[]` hamare *bheje hue* message ki delivery receipt hai (sent/delivered/read/failed). Inhe user message ki tarah treat karna galat hoga, isliye abhi sirf log (M3 me save). Log me sirf message id, status aur error code, number nahi.
3. **Unsupported types** (sticker, location, video, reaction...) bhi `messages` me `type=unsupported` se save hote hain, taaki baad me user ko polite reply de sakein.
4. **Foreign `phone_number_id`**: kisi aur number ke events ignore, par 200 (warna Meta retry karega).

## Important technical decisions
- **Signature = HMAC-SHA256 on raw bytes, timing-safe compare.** `rawBody: true` Nest me on kiya. Parse kiye hue JSON ko dobara `JSON.stringify` karoge to spacing/key order badal sakta hai aur HMAC match nahi karega; isliye exact bytes chahiye (test: same JSON, alag formatting = 401). `timingSafeEqual` isliye ki normal `===` compare jaldi return hota hai aur timing se secret guess kiya ja sakta hai.
- **Idempotency ki do layers.** Meta *at-least-once* deliver karta hai (timeout ya non-200 par retry). Layer 1: DB me `wa_message_id` UNIQUE + `ON CONFLICT DO NOTHING`. Layer 2: BullMQ `jobId = waMessageId`, to same job do baar nahi banta.
- **Duplicate par bhi enqueue try karte hain (spec se ek farak, jaanbujhkar).** Scenario: message DB me save hua, phir Redis down, hum 500 dete hain, Meta retry karta hai. Agar "duplicate = skip" karte, to job kabhi nahi banta aur message kho jaata. Ab retry par row duplicate hai par `queue.add` job bana deta hai; agar job pehle se hai to jobId ki wajah se no-op. Integration test isi poore scenario ko chalata hai.
- **Fast 200 + queue.** Webhook me sirf DB insert aur Redis push; AI/media download worker me. Handler 800 ms se upar jaye to warning log. 10-message batch ka test 1 s se kam me hota hai.
- **DB/Redis down = 500, signature fail = 401, baaki sab (unsupported, foreign, malformed) = 200.** Galat signature ya server error par Meta ko retry chahiye; kharab-par-valid payload par retry bekaar hai.
- **Phone number: hash for lookup, encryption for sending.** `wa_phone_hash` = HMAC-SHA256(pepper, number) (deterministic, to user dhoondh sakte hain, par bina pepper ke reverse/guess nahi). `wa_phone_enc` = AES-256-GCM, har baar naya random 12-byte IV, format `v1:<iv>:<tag>:<ciphertext>` (`v1` = future key rotation ke liye). GCM ka auth tag tamper pakadta hai. Number kabhi plain DB/log/queue me nahi.
- **Job payload me PII nahi.** Sirf ids, type, media id, button id. Worker DB se jo chahiye padh lega. Isse Redis me (jo kam secure hota hai) koi phone/text nahi rehta. Media `filename` payload me jaata hai par redact hoke (naam ho sakta hai, jaise `Ramesh_Sharma_Rx.pdf`).
- **`body_redacted`**: phone, Aadhaar-jaisa 12-digit, email, 6-digit PIN regex se `[REDACTED_*]`. Ye gateway ka safety net hai; poora Presidio AI service me M6 me. Trade-off: koi bhi akela 6-digit number (jaise platelets 150000) PIN maan liya jaata hai, over-redact safe side hai.
- **Concurrent first messages = ek hi user.** Prisma `upsert` unique hash par ek atomic `INSERT ... ON CONFLICT` hota hai; 8 parallel requests ka test 1 user deta hai.
- **`last_inbound_at` sirf aage badhta hai** (24-hour window ke liye): purana retry hua message window nahi badhata.
- **Rate limit 300/min** (`@nestjs/throttler`, in-memory, per instance): abuse se bachav, Meta ke bursts se nahi.
- **`messages.type` me `unsupported` add kiya** (naya migration `add_unsupported_message_type`), CLAUDE.md §6 me ye value nahi thi.
- **Error filter fix:** body-parser ke errors (413 bahut bada body) ab 413 jaate hain, 500 nahi; original message nahi dikhate kyunki JSON ka snippet (PHI) ho sakta hai. 500 par log me sirf stack frames, message nahi.

## Production-ready points
- **Security:** har POST signed; secrets (`WA_APP_SECRET`, `WA_VERIFY_TOKEN`, `PHONE_HASH_PEPPER`, `ENCRYPTION_KEY`) env validation me required, aur production me placeholder/dev key reject. 401 log me sirf request_id. Body limit 1 MB.
- **Reliability:** at-least-once ke liye idempotent har step, retries (BullMQ `attempts: 5`, exponential backoff), failed jobs `removeOnFail: false` (DLQ M15 me), Redis timeout 2 s taaki webhook latka na rahe, worker/queue graceful close.
- **Privacy tests:** integration test saare text/jsonb columns me phone number search karta hai (0 milna chahiye, `wa_phone_enc` me bhi), aur pino logs capture karke check karta hai ki number, message text, WhatsApp profile name kahin nahi.
- **Testing:** gateway 137 unit (crypto, redaction, signature + guard, parser har fixture, env), 24 e2e bina Docker ke (GET handshake, 401 cases, 200 for status/foreign/garbage, DB down par 500, 413, 429), 26 integration real Postgres/Redis par (dedupe, batch, concurrency, Redis-down repair, worker, PII).
- **Manually verify kiya:** `make webhook` se 200 + DB row + worker log; same fixture dobara = koi nayi row/job nahi; galat signature = 401; GET handshake `123`.
- **Honest gaps:** worker ka real kaam (M3+) baaki; throttler per-instance hai (multi-instance me total limit zyada); Jest e2e me kabhi-kabhi parallel worker "failed to exit gracefully" warning aati hai (tests pass hote hain, in-band me nahi aati); real Meta se end-to-end test (ngrok) abhi nahi kiya.

## Interview me kaise bolna hai
"M2 me maine WhatsApp ka inbound webhook banaya. Meta GET se verify karta hai aur POST se events bhejta hai. Har POST ka HMAC-SHA256 signature raw body par timing-safe compare se check hota hai, kyunki re-serialised JSON se signature match nahi hota. Phir payload zod se parse hota hai, user phone ke hash se dhoondha ya banaya jaata hai, number AES-GCM se encrypted rakha jaata hai, message DB me save hota hai aur BullMQ queue me job jaata hai, aur hum turant 200 dete hain. Meta at-least-once deliver karta hai, isliye idempotency do layer me hai: DB me unique wa_message_id aur queue me jobId. Ek subtle cheez: agar save ke baad Redis fail ho jaye to retry par duplicate par bhi enqueue karte hain, warna message kho jaata. Queue payload aur logs me koi phone number ya text nahi hota, aur ye integration tests se verify hota hai."

## Possible interview questions
1. **Agar Meta same message 3 baar bheje to?** Pehli baar row insert + job. Dusri/teesri baar `ON CONFLICT DO NOTHING` se row nahi banti, aur `jobId` same hone se job bhi nahi banta. Teeno ko 200 milta hai.
2. **DB ya Redis down ho to?** 500 dete hain taaki Meta baad me retry kare. Redis fail hone par row save ho chuki hoti hai; retry par duplicate dikhta hai par enqueue phir bhi hota hai, to message nahi khota.
3. **Signature verify me raw body kyun chahiye?** HMAC exact bytes par bana hai. Parse karke dobara serialise karne par whitespace/order badal sakta hai aur signature fail hoga.
4. **`timingSafeEqual` kyun, `===` kyun nahi?** `===` pehla alag byte milte hi return karta hai, to response time se attacker signature byte-by-byte guess kar sakta hai. Constant-time compare ye leak band karta hai.
5. **Phone number hash aur encrypt dono kyun?** Hash lookup ke liye (deterministic, search kar sakte hain par reverse nahi). Encryption sending ke liye (decrypt karke message bhejna padta hai). Ek hi cheez dono kaam theek se nahi kar sakti.
6. **Webhook me hi AI kyun nahi chalate?** Meta ko jaldi jawab chahiye; AI 20-30 s leta hai. Queue se webhook halka rehta hai, aur retries/backoff worker sambhalta hai.
7. **Statuses aur messages me fark?** Messages user ne bheje; statuses hamare bheje message ki delivery receipts. Alag treat karte hain, status se user ya message row nahi banti.
