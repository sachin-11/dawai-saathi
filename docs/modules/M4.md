# M4 — Onboarding, consent, commands aur DELETE

## Is module me kya banaya
Echo bot ki jagah ek asli conversation entry point: `InboundRouter`. Naya user pehle bhasha chunta hai (हिन्दी / English), phir consent message padhkar "I agree" ya "Not now" dabata hai. Consent ke baad hi bot kuch process karta hai. Commands bhi bane: `HELP`, `LANGUAGE`, `STOP REMINDERS` / `START REMINDERS`, `MEDS`, aur `DELETE` (confirmation ke baad user ka saara data hard delete, DPDP right to erasure). Emergency keywords (chest pain, saans nahi, aatmahatya...) har user ke liye, consent se bhi pehle, pakde jaate hain aur 112 / 108 (self-harm me Tele-MANAS 14416) ka message turant jaata hai. AI calls, reminder scheduling aur caregiver features is module me nahi hain.

## Kyun zaroori tha
Healthcare bot me "pehle permission, phir kaam" legal aur ethical rule hai (§2.7). Bina consent koi photo download ya process hui to privacy ka dhaancha toot jaata hai. Aur DPDP Act ke hisaab se user ko apna data mitane ka aasaan, poora aur sachcha tareeka chahiye, sirf "soft delete" nahi. Emergency me bot ko "pehle consent do" nahi kehna chahiye: jaan ka mamla pehle.

## Kaise kaam karta hai
```
Meta ──► webhook ──► (text yahin memory me hai) classify: emergency? command?  ──► job.signals (chhote enums, text nahi)
                     user row save; body_redacted = null agar consent nahi diya
                                        │
                                        ▼  inbound queue
                              InboundRouter.route(job)
   1. emergency signal?  ──► 112/108 (+14416)  [sabke liye, consent se pehle bhi, queue priority 1]
   2. DELETE / HELP / delete buttons ──► (har step me kaam karte hain)
   3. onboarding_step != done ──► OnboardingService  (kuch bhi process nahi, media download nahi)
   4. LANGUAGE / STOP-START REMINDERS / MEDS
   5. baaki sab ──► (DEV_ECHO_BOT ? echo : placeholder)   [M5 me AI aayega]

Onboarding state machine:

   [language] --lang:hi / lang:en--> [consent] --consent:yes--> [done]
       ^  kuch bhi aur: buttons dobara        |  consent:no: "theek hai" (consent me hi rehta hai)
       |                                      |  photo/text: sirf consent reminder, kuch process nahi
       +--------------------------------------+

DELETE:  "DELETE" ─► buttons [Yes/No] + Redis pending:delete:{userId} (TTL 5 min)
         "Yes" + key hai ─► user-deletion job   |  key nahi (expire) ─► "expired", kuch delete nahi
         job: S3 prefix ─► queues ke user jobs ─► pending keys ─► DB transaction ─► final message
```
1. **Text router ko nahi dikhta.** Queue me text daalna PHI hota (§2.6), aur consent se pehle text store bhi nahi karte. Isliye webhook, jahan text pehle se memory me hai, do pure functions chalata hai (`detectEmergency`, `parseCommand`) aur sirf unka nateeja (`signals: { emergency?, command? }`) job me jaata hai. Router bina text dekhe sahi branch chunta hai.
2. **Buttons id se pehchane jaate hain, title se nahi** (`lang:hi`, `consent:yes`, `delete:confirm`...). Title translate hota hai aur badal sakta hai; id hamari control me hai.
3. **Retry-safe replies:** `ReplySession` har reply ko `replyIndex` 0, 1, 2... deta hai, to inbound job retry hone par wahi outbound job ids bante hain aur user ko reply do baar nahi jaata (M3 ki jobId logic).

## Important technical decisions
- **Consent-first + data minimisation:** consent se pehle `messages.body_redacted = null` (sirf type/time metadata), media kabhi download nahi hota (router `MediaService` ko chhuta hi nahi), aur photo bhejne par sirf consent reminder milta hai. Consent ke baad user ko photo dobara bhejni padti hai; purani media process nahi hoti.
- **Emergency consent se pehle:** safety rule §2.2 sabse upar hai. Ye gateway ka always-on keyword net hai (en / Devanagari / Hinglish, nukta-chandrabindu normalisation ke saath: ज़हर = जहर, साँस = सांस). AI service ka classifier M6 me aayega, par ye tab bhi chalega jab AI service down ho. Safety-first hone se false positives hote hain ("no chest pain" bhi trigger karega); ek bekar "112 call karo" ek chhoote hue emergency se bahut sasta hai.
- **Command parser me exact match (substring nahi):** "help me with my medicine" ya "delete this from my prescription" HELP/DELETE nahi hone chahiye, warna galti se data delete ho sakta hai. Case, spaces, trailing punctuation aur emoji ignore hote hain ("HELP!!", " help 🙏 "), `?` akela HELP hai.
- **DELETE ke liye confirmation + TTL:** Redis `pending:delete:{userId}` 5 minute me expire. Purana "Yes" button ghanton baad dabaya to kuch delete nahi hota. Confirm ke order me pehle erasure job enqueue + user mark, phir pending key hatate hain, taaki retry par "expired" na dikhe.
- **Hard delete ek transaction me:** users row delete (cascade se caregivers, messages, documents, medications, reminders), us user ke audit rows delete, aur ek **anonymous** `user_deleted` audit row insert, sab ek saath. Isse "user gaya" aur "audit row bani" ek hi event hain, aur retry par doosri audit row nahi banti. `audit_logs` par FK nahi hai (isi liye).
- **Erasure job ki order aur idempotency:** S3 pehle (`media/{userId}/`), phir Redis queues ke user jobs (completed outbound jobs me reply ka encrypted text hota hai, wo bhi hatate hain), phir pending keys, phir DB, phir final message. Final message user row hatne ke baad jaata hai, isliye job data me phone **encrypted** rakha jaata hai (job complete hote hi remove), aur `finalMessageSent` flag se dobara nahi jaata. Job do baar chale to koi fail nahi hota.
- **Erasure ke dauraan user ignore:** confirm par `users.deleted_at` set hota hai; router us user ko ignore karta hai (15 min tak, taaki atka hua job user ko hamesha chup na kar de).
- **Audit metadata me PII nahi:** `assertSafeAuditMetadata` sirf numbers, booleans, chhote machine tokens allow karta hai. Phone jaisa dikhne wala string (10-digit, 12-digit, 6-digit PIN), email, naam ya sentence reject.
- **Echo bot ab consent bypass nahi karta:** router pehle chalta hai; `DEV_ECHO_BOT` on ho tab bhi echo sirf consent ke baad ke users ke liye hai.
- **Emergency reply queue priority 1** (BullMQ), taaki doosre sends ke peeche na atke. Language chuni hi nahi to message Hindi + English ek saath.

## DPDP Act ke principles project me kaise map hue
| Principle | Kahan |
|---|---|
| Free, specific, informed **consent** | `consent.v1.body`: kya store hota hai, retention (`MEDIA_RETENTION_DAYS`), "doctor nahi", DELETE, privacy link. Version `consent_version = v1`, time `consent_at`, audit `consent_given`. Consent se pehle koi processing nahi |
| **Purpose limitation / data minimisation** | Consent se pehle sirf metadata; media download nahi; audit me PII nahi; Redis me readable PHI nahi |
| **Storage limitation** | Photos `MEDIA_RETENTION_DAYS` baad auto-expire (bucket lifecycle, M1) |
| **Right to erasure** | `DELETE` → confirmation → `user-deletion` job: S3 + Redis + DB hard delete, anonymous audit |
| Transparency / accountability | `audit_logs`: consent_given/declined, language_changed, reminders on/off, delete_requested, user_deleted |

## Production-ready points
- **Safety:** emergency pehle, consent-first, DELETE confirmation, exact-match commands, anonymous audit.
- **Reliability:** har state change conditional (`updateMany where onboardingStep = ...`), retries idempotent, erasure job 5 attempts exponential backoff, permanent fail par `USER ERASURE FAILED PERMANENTLY` error log (M15 me alert).
- **Testing:** gateway 639 unit (router ke har branch, onboarding ki step x input table, commands aliases + negatives, har bhasha ke emergency phrases, deletion service ke steps + idempotency, queue cleanup, audit PII guard, button titles <= 20 chars, consent body <= 1024), 25 e2e, 69 integration real Postgres/Redis/MinIO. Acceptance E2E: naya number → language → consent → photo MinIO me → DELETE → confirm → har `user_id` wali table khali, S3 prefix khali, sirf ek anonymous audit row, final message ek baar, wahi number dobara = fresh onboarding.
- **Process me bhi dekha:** gateway + mock Graph par `make webhook` se poora flow chala, aur logs me koi phone/text nahi mila.
- **Honest gaps (known limitations):** DB **backups / PITR** me deleted data apni retention tak reh sakta hai (production retention policy M17/M18 me tay hogi aur privacy policy me likhni hai); inbound/outbound jobs jo erasure ke waqt *active* hain hat nahi sakte (wo user missing dekhkar khud chhod dete hain, aur unme sirf ids hote hain); voice notes par emergency check STT (M13) ke baad hi lagega; "consent wapas lena" abhi sirf `DELETE` se hota hai (alag withdraw command nahi); real Meta number par manual test baaki.

## Interview me kaise bolna hai
"M4 me maine WhatsApp bot ka consent-first conversation layer banaya. Naya user pehle bhasha chunta hai, phir consent message accept karta hai; tab tak koi photo download ya process nahi hoti aur text bhi store nahi hota. Emergency keywords ka ek always-on net hai jo consent se bhi pehle 112/108 ka jawab deta hai. Text queue me nahi jaata: webhook usse emergency/command signals me badal deta hai aur router sirf wahi dekhta hai. DELETE par confirmation aur 5 minute ka Redis TTL hai, phir ek job S3, Redis queues aur DB se user ko hard delete karta hai: DB me ek transaction me user, uske audit rows hataye jaate hain aur ek anonymous 'user_deleted' record likha jaata hai. Job idempotent hai, to beech me crash ho to dobara chalane par koi galti nahi. Sab kuch integration tests se verify hai, aur backups ki retention ek documented limitation hai."

## Possible interview questions
1. **Deletion beech me fail ho jaye to?** Job me 5 attempts hain (exponential backoff) aur har step re-runnable hai: S3 delete dobara karna safe, queue cleanup safe, DB transaction me user nahi mila to skip (audit dobara nahi), final message ka flag job me hai. Phone job data me encrypted rehta hai taaki retry me bhi final message ja sake. Permanent fail par error log (alert M15), aur `deleted_at` marker 15 min baad expire hota hai, to user hamesha chup nahi rehta.
2. **Backup me data reh gaya to?** Honest jawab: live DB aur S3 se data hat jaata hai, par DB backups / point-in-time recovery me wo apni retention (jaise 7-35 din) tak reh sakta hai. Ye DPDP ke liye accept hota hai agar backup se restore par erased users dobara dikhne se pehle unka erasure re-apply ho aur policy me likha ho. Production me retention chhoti rakhni aur privacy policy me batana hai (M17/M18).
3. **User consent wapas le to?** Abhi "withdraw" ka matlab hai `DELETE`, jisse sab mit jaata hai. Alag "sirf processing roko par data rakho" option baad me add kiya ja sakta hai (consent version bump karke re-consent bhi).
4. **Command parser me substring kyun nahi?** "help me with my medicine" HELP ko trigger karta, aur "delete this" DELETE ko. DELETE ke liye to confirmation bhi hai, par galat command UX kharab karta hai; exact match + alag confirmation do layers hain.
5. **Emergency check consent se pehle kyun?** Jaan ka mamla consent se upar hai, aur ye check kuch store nahi karta aur sirf ek fixed number-message bhejta hai. AI service down ho tab bhi kaam karta hai.
6. **Text queue me kyun nahi daala?** Queue/Redis PHI store nahi hai. Webhook me text pehle se memory me hota hai, wahin se chhote signals nikaal lete hain.
7. **Same number delete ke baad phir aaye to?** Naya user row (naya uuid) aur fresh onboarding; purana kuch nahi bachta.
