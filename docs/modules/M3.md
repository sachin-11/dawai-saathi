# M3 — Messaging client (outbound) + media download

## Is module me kya banaya
Bot ko bolna sikhaya. Ek hi class `WhatsAppClient` Graph API se baat karti hai (text, buttons, template, blue ticks, media URL, media download). Har reply seedha nahi bhejte: `OutboundService.enqueue()` use BullMQ ke `outbound` queue me daalta hai, aur `OutboundWorker` rate-limit ke saath bhejta hai, retry karta hai aur `messages` me outbound row save karta hai. Inbound photo/PDF/voice note S3 (MinIO) me stream hoke jaata hai. Webhook ke delivery statuses (`sent/delivered/read/failed`) ab DB me save hote hain. Saath me i18n (hi/en), template registry aur ek dev-only echo bot hai jisse poora loop real Meta number par test hota hai. Consent, AI aur reminders is module me nahi hain.

## Kyun zaroori tha
M2 sirf sunta tha. Reply bhejna aasan lagta hai (ek HTTP call), par production me bahut cheezein galat ja sakti hain: Meta slow ya down ho, rate limit lage, 24 ghante ki window band ho, retry se user ko same message do baar mil jaaye, ya media URL expire ho jaaye. Ye sab ek jagah (client + queue) sambhale gaye hain taaki baaki modules (consent, reminders, AI reply) sirf `enqueue()` bulaayein.

## Kaise kaam karta hai
```
User ──msg──► Meta ──POST──► Webhook (M2) ──► inbound queue ──► InboundWorker
                                                                    │ (DEV_ECHO_BOT=true)
                                   markAsRead ◄─────────────────────┤
                                   MediaService: getMediaUrl → download(stream) → S3 (SSE) → messages.media_s3_key
                                                                    │
                                              OutboundService.enqueue(userId, reply)   (24h window pre-check)
                                                                    ▼
                          outbound queue  (jobId = sourceMessageId_replyIndex, payload ENCRYPTED)
                                                                    ▼
          OutboundWorker (limiter 20/s) ─► OutboundService.deliver ─► decrypt phone (memory only)
                                                │  24h window? ─ closed ─► template fallback / fail
                                                ▼
                                        WhatsAppClient ──► Graph API ──► wamid
                                                │ wamid job data me, phir messages(direction=out) me save
Meta ──status webhook──► StatusUpdater ──► messages.delivery_status (sent < delivered < read; late events ignore)
```
1. **Outbound bhi queue se kyun:** reply bhejna slow aur failure-prone hai. Queue se (a) retry/backoff ek jagah, (b) throughput cap (Meta ke limits), (c) worker crash par job nahi khota, (d) inbound worker latka nahi, (e) same `jobId` se duplicate nahi.
2. **24-hour window:** user ke aakhri message ke 24 ghante tak free-form text/buttons allowed. Uske baad sirf Meta-approved **template** messages. Rule ek function `isWithinWindow()` me hai (strictly 24 h se kam = open; exactly 24 h = closed, conservative). Check do baar: `enqueue` par (jaldi error) aur `deliver` par (queue me der ho sakti hai). Template fallback diya ho to wo jaata hai, warna job permanent fail.
3. **Templates:** `TemplateRegistry` internal naam → Meta naam + language + params ka order. Koi service JSON haath se nahi banata. Texts `docs/whatsapp-templates.md` me (Meta ko submit karne ke liye).

## Retry strategy: kaunsa error retry hota hai aur kaunsa nahi
| Error | Kya hota hai |
|---|---|
| Network (connect refuse/DNS) | client andar hi retry (4 attempts, exponential backoff + jitter) |
| HTTP 5xx, HTTP 429 | client retry, `Retry-After` header ho to wahi (agar lamba ho) |
| Code `130429`, `131056` (rate limit, HTTP 400 aata hai) | client retry nahi karta; `retryable=true`; queue 30 s, 60 s... backoff se retry |
| `131047` (24h window band) | **retry nahi**: template chahiye. Job turant fail |
| `131026` (undeliverable) | retry nahi |
| `190` (token invalid/expired) | retry nahi, `error` level log (M15 me alert) |
| Baaki 4xx (400, 404...) | retry nahi |
| Timeout/connection reset **send** ke baad | client retry nahi (ambiguous), queue retry karta hai |

**Sabse tricky baat:** WhatsApp API me idempotency key nahi hoti. Agar request Meta tak pahunch gayi par jawab nahi aaya (timeout), to retry se user ko same message do baar mil sakta hai. Isliye send ke liye client sirf wahi retry karta hai jahan request pakka Meta tak nahi pahunchi (connect-phase errors) ya Meta ne saaf mana kiya (429/5xx). Read-only calls (markAsRead, getMediaUrl, download) ko har failure par retry karte hain kyunki unme duplicate ka nuksaan nahi.

## Idempotent sending: "user ko same reply 2 baar na jaaye"
- **Layer 1: deterministic jobId** `sourceMessageId_replyIndex`. Inbound job retry ho kar wahi reply dobara enqueue kare, to BullMQ same job maan leta hai (integration test: do baar enqueue = ek send).
- **Layer 2: resume.** Meta ka `wamid` milte hi job data me likh dete hain (`sentWaIds`), DB insert se **pehle**. Agar DB insert fail ho aur job retry ho, to wo dobara nahi bhejta, sirf (idempotent, `ON CONFLICT DO NOTHING`) insert dohrata hai. Lambe text ke multi-part reply me jo parts ja chuke hain wo skip hote hain.
- **Bachi hui chhoti window:** send ho gaya aur `updateData` se pehle process crash: tab dobara send ho sakta hai. Rare hai, aur documented limitation hai.

## Media: stream, limits, S3 key
- `getMediaUrl(id)` → mime/size/sha256 milta hai. URL jaldi expire hota hai, isliye turant download.
- **Allowlist:** `image/jpeg, png, webp, application/pdf, audio/ogg, mpeg, mp4, aac`. SVG/HTML/zip/video reject. `audio/ogg; codecs=opus` ko normalise karte hain.
- **Size limit `MAX_MEDIA_MB` (10):** teen jagah check: Meta ka `file_size`, download ka `Content-Length`, aur **stream ke dauraan** (kyunki header jhootha ho sakta hai). Limit paar hui to upload abort, kuch store nahi.
- **Memory me poori file nahi:** Meta → size/hash guard (Transform stream) → S3 multipart upload (5 MB parts).
- **sha256:** Meta ka hash ho to match karte hain; mismatch par object delete + error.
- **S3 key** `media/{userId}/{yyyy}/{mm}/{messageId}.{ext}`: sirf internal UUID aur fixed extension. Phone number ya user ka filename (jaise `Ramesh_Sharma_Rx.pdf`) nahi, kyunki key logs aur bucket listings me dikhti hai.
- **Security extra:** media URL Meta ke jawab se aata hai aur download par hum bearer token bhejte hain. Isliye token sirf HTTPS + Meta ke hosts (`*.fbsbx.com`, `*.facebook.com`, `*.whatsapp.net`, `*.fbcdn.net`) par jaata hai.
- **Encryption:** S3 server-side encryption (`AES256`). Local MinIO ko KMS key chahiye (compose me local-only key); AWS par SSE-S3 default.

## Delivery statuses aur out-of-order events
Webhooks order me nahi aate. `read` pehle aa sakta hai aur `delivered` baad me. Isliye har status ke liye "kaunse purane states ko replace kar sakta hai" table hai: `sent` sirf khali ko, `delivered` null/sent ko, `read` null/sent/delivered ko, `failed` sirf null/sent ko (`failed` kabhi `delivered/read` nahi todta). Ek UPDATE me, race-free.

**Ek aur race:** hum outbound row Meta ka jawab aane ke **baad** insert karte hain (`wa_message_id` Meta deta hai). Bahut tez `delivered` receipt insert se pehle aa sakti hai. Row na mile to 1 s, 3 s, 10 s par retry (in-process timers; receipts best-effort hain isliye durable job nahi).

## Important technical decisions
- **Queue payload me message text ENCRYPTED** (AES-256-GCM, wahi key jo phone ke liye). Reply me health info hoti hai aur Redis PHI store nahi hai.
- **Client sirf transport-level retry karta hai** (429, 5xx, connect errors). Code-based rate limits queue ko chhodte hain jo 30 s+ ruk sakta hai; request ke andar 30 s sleep karna galat hota.
- **`WhatsAppApiError { httpStatus, kind, code, subcode, retryable }`** typed error; message redacted + 300 chars tak, kyunki Meta kabhi value echo karta hai.
- **`nock` 14** (15 ESM-only hai, hamara Jest CJS hai), `@aws-sdk/lib-storage` streaming upload ke liye.
- **Echo bot sirf dev:** `DEV_ECHO_BOT=false` default; `NODE_ENV=production` me `true` ho to app **boot hi nahi hoti** (env validation). Ye consent bypass karta hai (§2.7), isliye M4 consent flow live hone se pehle hatana hai.
- **Outbound buttons ka DB type `button`** (enum me `interactive` nahi), direction `out` se alag hota hai.
- **Lambe text ka split client me nahi, service me:** `sendText` ek hi message (<= 4096) bhejta hai; `OutboundService` paragraphs par todta hai aur ek job me parts **kram se** bhejta hai (alag jobs me order bigad sakta tha).

## Production-ready points
- **Security:** token kabhi log nahi hota (test), phone sirf memory me decrypt hota hai, media host allowlist, key me PII nahi, payload encrypted, DEV_ECHO_BOT production me refuse.
- **Reliability:** bounded retries, jitter, `UnrecoverableError` se permanent errors turant fail, `removeOnFail: false` (DLQ M15), throughput limiter, graceful worker close.
- **Testing:** gateway 332 unit (client with nock: bodies, retries, error mapping, no-token-in-logs; window boundary; splitter; registry; i18n parity; media allowlist/size/sha; outbound idempotency/resume; backoff), 25 e2e, 45 integration real Postgres/Redis/MinIO (echo loop exact payload, media -> MinIO with SSE, statuses + race, retry, non-retryable fail, template fallback, presigned URL, deletePrefix). Process-level check: gateway + chhota mock Graph server par `make webhook` se read receipt + Hindi echo.
- **Honest gaps:** real Meta number ke saath test aapko karna hai (README guide); token expiry par sirf `error` log hai (alert M15 me); outbound order alag-alag jobs ke beech guaranteed nahi (ek logical reply ek job me bhejo); rate-limit retry (30 s+) ka end-to-end test nahi, sirf backoff function ka unit test.

## Interview me kaise bolna hai
"M3 me maine WhatsApp ka outbound side banaya. Ek typed `WhatsAppClient` hai jo timeout, jitter ke saath retry aur Meta ke error codes ko typed errors me map karta hai. Replies seedha nahi bhejte, BullMQ ke outbound queue se bhejte hain, jahan rate limit, backoff aur deterministic jobId se duplicate roka jaata hai. Ek important cheez: WhatsApp API me idempotency key nahi hoti, isliye send par sirf wahi retry karte hain jahan request pakka nahi pahunchi, aur Meta ka message id job me turant likh dete hain taaki retry me dobara na jaaye. 24-hour window ka rule ek function me hai aur band hone par template fallback hota hai. Media ko memory me laye bina S3 me stream karte hain, size aur mime limits ke saath, aur key me koi PII nahi daalte. Delivery statuses out-of-order aate hain, to state machine se sirf aage badhne dete hain."

## Possible interview questions
1. **Meta API down ho to?** Client chhote retries karta hai, phir job BullMQ me exponential backoff ke saath 5 attempts tak retry hota hai; row/progress safe rehta hai, user ko duplicate nahi jaata. Webhook (inbound) alag chalta hai, to hum messages receive karte rehte hain; reply baad me jaate hain. Permanent fail par job `failed` me rehta hai (DLQ).
2. **Rate limit kaise handle kiya?** Do jagah: BullMQ `limiter` (20/s) taaki hum limit se pehle hi ruk jaayein, aur agar Meta `130429/131056` de to client andar retry nahi karta, queue 30 s+ backoff se retry karta hai. Pair rate limit (ek user ko 6 s me ek message) ko bhi yahi sambhalta hai.
3. **Media URL expire ho jaaye to?** URL minutes me expire hota hai, isliye `getMediaUrl` ke turant baad download. Agar phir bhi fail, job retry me `getMediaUrl` dobara bulaata hai (fresh URL), isliye expire hone se dikkat nahi. Media id ke bhi expire hone par (kuch din) error aata hai jo user ko "dobara bhejein" kehkar handle hoga.
4. **Retry se user ko do baar message na jaaye, kaise?** jobId deterministic, wamid ko job data me turant likhna, DB insert idempotent, aur send par ambiguous failures ka client retry band.
5. **Outbound ko queue me kyun daala, seedha kyun nahi?** Retry/rate-limit ek jagah, worker crash safe, inbound processing latka nahi, aur duplicate control jobId se.
6. **24-hour window band ho to?** `enqueue` par typed `WindowClosedError`; template fallback ho to wo bhejte hain. Template ka text Meta se pehle approve karana padta hai.
7. **Media me security kya dekhi?** Mime allowlist (SVG nahi), size limit stream ke dauraan bhi, sha256 verify, S3 SSE, key me PII nahi, aur bearer token sirf Meta hosts ko.
