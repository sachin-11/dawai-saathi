# M15 — Observability, rate limits, cost guard

## Is module me kya banaya

Ek WhatsApp message ab **ek trace** hai: webhook → queue → worker → AI service → har graph node → outbound send. Saath me Prometheus metrics (dono apps), JSON logs me wahi `trace_id`, Grafana ke 6 dashboards, SLOs + burn-rate alerts + 12 runbooks. Safety ke liye: per-user rate limits (emergency kabhi nahi rukti), abuse auto-block, dead-letter queues (koi message silently drop nahi), aur LLM daily budget guard jo 4 modes me degrade karta hai (`normal → economy → essential → exhausted`). Sab kuch PHI-safe: attribute allowlist, low-cardinality labels, redacted logs.

## Kyun zaroori tha

Production me "kuch toot gaya" ka pata users se nahi, hamare dashboard se chalna chahiye. Health app me sabse bura failure **silence** hai: user ne dawai ka sawal bheja aur jawab nahi aaya. Aur LLM bill ek bug ya ek abusive user se ek raat me phat sakta hai. M15 teen sawal ka jawab deta hai: *kya toot raha hai?* (traces/metrics/alerts), *kaun nuksan kar raha hai?* (rate limits/blocks), *kitna kharcha ho raha hai?* (budget guard).

## Kaise kaam karta hai

```
Meta ──webhook──▶ gateway ──enqueue(job + traceparent)──▶ BullMQ inbound
                    │ span: POST /webhook            │
                    │ metric: wa_inbound_total       ▼
                    │                       InboundWorker (WorkerFactory)
                    │                         span "inbound process" (child of the webhook span)
                    │                         ├─ rate limiter + block check  (emergency/DELETE/HELP skip it)
                    │                         ├─ budget state ◀── Redis  (INCRBY micro-USD)
                    │                         └─ AI client span ──traceparent header──▶ ai-service
                    │                                                       span POST /v1/process
                    │                                                       └─ graph.<node> spans
                    ▼                                   reply ◀──────────────┘
              outbound queue (+ traceparent) ─▶ OutboundWorker ─▶ Graph API
                    metric: reply_latency_ms{intent} = received → accepted by WhatsApp
Job fails 5x ─▶ <queue>-dlq (ids + error code, no payload) ─▶ user told once / alert
```

- **Logs vs metrics vs traces.** *Metrics* batate hain "kitna aur kab" (p95 latency, error rate): sasta, aggregate, alert yahin se. *Traces* batate hain "ek request me kahan time gaya": ek message ka poora raasta. *Logs* batate hain "us moment pe kya hua": event ka context. Teeno ek `trace_id` se jude hain: Grafana me metric spike → Tempo me slow trace → Loki me us trace ke logs → Langfuse me prompt/LLM calls (span attribute `dawai.langfuse_trace_id`, aur Langfuse trace output me `otel_trace_id`).
- **Trace context BullMQ ke through.** Redis queue HTTP nahi hai, to header nahi chalta. `withTrace(data)` job data me ek chhota field `_tp` (W3C `traceparent`: trace id + span id + flags, koi user data nahi) daalta hai. Worker `WorkerFactory.instrument` me `contextFromCarrier(job.data)` se context nikalta hai aur "inbound process" span ko webhook span ka child banata hai. Retry me bhi `_tp` job ke saath rehta hai, to retries usi trace me dikhte hain.
- **PHI-safe telemetry (allowlist approach).** Blocklist ("phone mat bhejo") hamesha kuch bhool jata hai. Hum ulta karte hain: ek span attribute tabhi export hota hai jab uski key allowlist me ho (ya `dawai.*` ho) **aur** value chhoti primitive ho jisme phone/email jaisa kuch na ho. URLs (presigned S3 signature), DB statements, exception messages, status text sab drop. Ye `ScrubbingExporter` export se thik pehle chalta hai, dono apps me; tests me phone, email, text, URL daalke dikhaya ki gayab ho jata hai. Live Tempo trace me exported attribute keys ki poori list sirf `dawai.*` aur 6 `http.*` thi. Metrics me labels bhi allowlist se: `user_id`, drug name, text kabhi label nahi (test fail karta hai).
- **Sampling.** Har trace record hoti hai; `TailSamplingProcessor` trace khatam hone pe faisla karta hai: error ya emergency wali trace **hamesha** (100%), baaki `OTEL_SAMPLE_RATIO` (0.2). Ratio ka faisla trace id ka pure function hai, to gateway aur AI service bina baat kiye same faisla lete hain (TypeScript aur Python ke parity vectors test me).
- **Rate limits.** Redis sorted-set sliding window, ek Lua script (atomic: 50 parallel hits, limit 10 → exactly 10 pass, integration test). Per user: 10/min, 200/day, 20 docs/day, 30 voice/day, 3 caregiver invites/day. Limit lagne pe **ek** friendly notice (marker `SET NX`), baaki chupchap drop. Retry hone wala job quota nahi khata (hit ka member = message id). **Emergency, DELETE, HELP limiter se pehle handle hote hain**, block se bhi nahi rukte (DELETE ek legal haq hai). Ek din me `RL_BLOCK_AFTER_WINDOWS` se zyada limited windows → `users.blocked_until` (migration `m15_blocking`), ek notice, audit row, `cli user:unblock`.
- **DLQ aur "koi message silently drop na ho".** `WorkerFactory` har failure count karta hai; aakhri attempt ke baad job `<queue>-dlq` me jata hai (error code, attempts, trace id, uuids; payload nahi, kyunki payload me encrypted PHI ho sakta hai). Inbound DLQ → user ko `common.error_try_again` **ek hi baar** (outbound jobId `<messageId>_99`, wahi jo AI-failure wala message use karta hai, to BullMQ dedupe karta hai). `user-deletion` DLQ → turant alert (`UserErasureDeadLetter`). Operator CLI: `dlq:list|retry|purge`, `user:unblock`, har kaam `audit_logs` me. Graceful shutdown: worker naye jobs lena band, `SHUTDOWN_GRACE_S` tak chal rahe jobs ko poora karne deta hai, phir forced close (job ka lock expire hoke doosra worker retry karta hai).
- **Cost guard.** Gateway `meta.cost_usd` Redis me micro-dollars me jodta hai (Asia/Kolkata din), state nikalta hai, har request me `options.budget_state` bhejta hai. AI service us state pe degrade: `economy` (70%+): text-role calls CHEAP model pe, spoken reply nahi. `essential` (90%+): sirf prescription extraction, emergency classifier, templates; lab report/voice/text sawal "busy". `exhausted` (100%+): sirf templates + emergency **rules**. **Emergency kabhi budget par depend nahi karta**: emergency rules aur template state padhte hi nahi (har state me test), gateway pre-check LLM se pehle hai, aur har "busy" template me 112/108 line hai. Per-user cap (`USER_DAILY_COST_USD`), per-request cap (`MAX_COST_PER_REQUEST_USD`, graph ke andar vision node se pehle rukta hai: "kam pages bhejein"), 23:55 IST daily cost report (aggregate only).

## SLOs kya chune aur kyun

Teen vaade: (1) 95% prescription/lab reply 30 s me aur 99% text reply 10 s me, (2) 99.5% inbound messages serve hon (DLQ me na jayein), (3) 99% reminders 2 min ke andar. Latency aur reminder wahi hain jo user feel karta hai; "served" isliye ki silence sabse bura failure hai. Availability of `/health/ready` nahi chuna: process healthy ho kar bhi kisi ko serve na kare to wo SLO jhoothi hai. Alerts **multi-window burn rate** se: 1h **aur** 5m dono ≥ 14.4× → page (budget 2 din me khatam), 6h aur 30m ≥ 6× → ticket. Long window "problem asli hai", short window "abhi bhi ho raha hai" bolti hai, to fix ke turant baad alert hat jata hai. Poori table `docs/slo.md` me; har alert ka runbook `docs/runbooks/` me (`runbook_url` annotation, CI check ki file exist karti hai).

## Important technical decisions

| Faisla | Wajah / trade-off |
|---|---|
| Tail sampling app ke andar (custom processor), Collector me production ke liye example | Head sampling error ko pehle se nahi jaanta. Trade-off: har process me thodi memory (max 2000 traces / 120 s buffer) |
| Allowlist exporter, blocklist nahi | Naya attribute galti se bhi PHI leak na kare. Trade-off: useful attribute add karne ke liye key allowlist me daalni padti hai |
| Budget gateway me, state request ke saath AI service ko | AI service stateless rehti hai (§4); gateway sab `meta.cost_usd` dekhta hai. Trade-off: contract me ek naya field (`options.budget_state`) |
| Rate limiter fail-open, budget guard fail-open | Toota hua guard product ko down na kare. Trade-off: Redis down ho to limits nahi lagte (queue aur cost cap phir bhi) |
| Pehle limiter, phir onboarding (HELP/DELETE/emergency uske pehle) | Spam consent flow tak na pahunche; legal/safety commands kabhi na rukein |
| Counters ko 0 se pre-create karna | Prometheus `increase()` pehli event ko 0 dikhata hai agar series pehli baar non-zero aaye; live test me exactly yahi dikha |
| Loki logs OTel Collector `filelog` se, Promtail nahi | Ek component kam |

## Production-ready points

- **Security:** `/metrics` Bearer token (production me required, env validation), PHI allowlist, redacted logs, DLQ me payload nahi, CLI audit.
- **Reliability:** DLQ + single user notice, graceful shutdown with deadline, fail-open guards, idempotent limiter (retry = quota nahi), startup + readiness probes (`/health/startup`, queue ping, AI reachability info-only, LLM circuit state).
- **Tests (is module me):** gateway 1193 unit (telemetry, limiter, budget, router gates, DLQ effects, parser), integration 163 (real Redis/BullMQ: Lua limiter, blocks, budget, DLQ, retry, shutdown, trace through a real job), e2e 44 (+ log-leak check: koi phone, Aadhaar-jaisa number, email ya user ke shabd 2 services ke logs me nahi), AI service pytest (metrics label allowlist, scrubbing, tail sampling, trace propagation, 4 budget states, emergency in every state, per-request cap), `promtool check rules` + `amtool check-config` + `check.py` (dashboard metric names asli, runbook files asli).

### Verification ne ye asli bugs pakde (aur fix hue)

1. Webhook ka fixed 300 req/min throttle 20 msg/s par 75% requests ko 429 de raha tha → `WEBHOOK_RATE_LIMIT_PER_MIN` (default 6000).
2. Counter jo pehli baar non-zero aaye, `increase()` use 0 dikhata hai → alert wale series 0 se pre-create.
3. SLO2 recording rule khali rehta jab tak pehla dead letter na ho → `or vector(0)`.
4. Retry hone wala inbound job limiter ka quota khata tha → hit idempotent (member = message id).
5. Ek hi user do baar block ho sakta tha → block sirf unblocked user par.
6. Forced worker close poori job ka intezaar kar leta tha → `FORCE_CLOSE_CAP_MS`.
7. Alertmanager container crash (gossip mesh, Docker me private IP nahi) → `--cluster.listen-address=`.
8. Log-leak test ka Aadhaar regex UUID ke 12-digit tukde par galat fire hota tha → lookaround.

### Verify NAHI hua (aur kyun)

- Asli Meta quality / template-status webhook payload: parser Meta docs se likha hai, live payload nahi dekha; tolerant hai (unknown → `OTHER`), recorded-style samples se unit-tested.
- Asli model costs: fake pricing se `cost_usd = 0`, isliye budget states Redis me spend inject karke dekhe; `pricing.yaml` ab bhi placeholders hai.
- Asli OS `SIGTERM`: Windows par process signal nahi bhej sakte; `WorkerFactory.close` ka in-flight-job behaviour real BullMQ se test hua, `enableShutdownHooks()` (M2 se) aage ka wiring Linux CI/M17 me check hoga.
- Provider outage live (LLM): breaker/fallback M5 ke tests me hain; live alert maine WhatsApp token error se dikhaya, `LlmErrorRateHigh`/`AllLlmProvidersDown` sirf rule syntax + metric names tak check hue.
- Containers ke docker JSON logs ka Loki path (`filelog/docker`): sirf host-run apps (`./logs/*.log`) ka path chala; Langfuse (`make up-obs` ka hissa) is baar start nahi kiya, `otel_trace_id` ka link sirf fake client se test hua.
- Prisma / DB spans nahi hain (Prisma engine ke liye alag instrumentation chahiye); HTTP, Express, ioredis, BullMQ (manual), AI client spans hain.
- Red-team patterns se auto-block: gateway ko injection-guard hit ka signal nahi milta (counter AI service me hai, `injection_dropped_total`, dashboard par). Abhi block sirf limited windows se hota hai.
- "Pre-user phone hash" limiter: user pehle message par ban jata hai aur wahi se limit hota hai; unknown numbers ki baadh webhook ke per-IP throttle se rukti hai. Load balancer ke peeche `trust proxy` M17 me dekhna hai.
- Screenshots fake-load ke hain (`docs/images/m15-dashboard-*.png`); LLM cost wale panels fake mode me "no data".

## Interview me kaise bolna hai

"M15 me maine system ko operable banaya. Har WhatsApp message ek OpenTelemetry trace hai jo webhook se queue, worker, AI service ke har graph node aur outbound send tak chalti hai; trace context BullMQ job data me `traceparent` ke roop me jata hai. Telemetry PHI-safe hai: span attributes allowlist se export hote hain aur metric labels bhi allowlist se, to user id ya drug name kabhi nahi nikalta. SLOs teen hain, aur alerts multi-window burn rate par, har ek ka runbook hai. Reliability ke liye dead-letter queues hain, user ko error ek hi baar milta hai, aur erasure ka DLQ turant page karta hai. Cost ke liye daily budget ka 4-state machine hai jo model sasta karta hai ya features band karta hai, par emergency path budget ko padhta hi nahi. Aur maine ye sab live stack par k6 se chalaya: isse webhook ka 300/min throttle aur counters ka pehli-event wala bug mila jo unit tests me nahi dikhe the."

## Possible interview questions

1. **Production me latency badh jaye to kaise debug karoge?** Overview dashboard: kaunsa intent (sirf documents = vision model, sab = queue/webhook). Queues dashboard: `queue wait p95` badha to workers kam hain; job duration badha to kaam slow. AI dashboard: node latency p95 se slow node, provider status aur fallback share. Phir Tempo me >30 s wali ek trace kholkar dekhta hoon span kahan lamba hai, aur Loki me us `trace_id` ke logs. Runbook `reply-latency.md` yahi kram deta hai.
2. **LLM bill achanak badh jaye to?** `LlmBudgetBurn80` alert pehle hi aa chuka hota hai (70% par economy mode apne aap lag jata hai). Dashboard par model/intent ke hisaab se cost dekhta hoon; ek user ho to `USER_DAILY_COST_USD` aur rate limits use rok chuke hote hain, abuse ho to auto-block. 100% par sirf templates + emergency rules chalte hain, to bill ki upar seema hai.
3. **Kisi user ka message kho gaya, kaise pata chalega?** Webhook me message `wa_message_id` ke saath save hota hai (unique), job `jobId = wamid`. Trace id ya request id se Tempo/Loki me dekhta hoon kahan tak gaya. Agar job fail hua to `<queue>-dlq` me entry hai (`cli dlq:list`), aur user ko ek "try again" gaya hoga. SLO2 isi ko napta hai: DLQ me gaya message "served" nahi gina jata.
4. **High cardinality metrics ka problem kya hai?** Prometheus har label combination ki alag time series banata hai. `user_id` ya drug name label ho to lakhon series: memory aur query dono phat jate hain, aur ye PHI bhi leak karta hai. Isliye labels sirf bounded machine tokens (`queue`, `intent`, `status`, ...) aur ek test allowlist enforce karta hai.
5. **Emergency ko rate limit ya budget kyun nahi rokta?** Galat rukne ki keemat bahut zyada hai. Emergency rules rate limiter se pehle chalte hain, budget state padhte hi nahi, aur "busy" template me bhi 112/108 line hai. Test har budget state me emergency check karta hai.
6. **Counter pehli baar non-zero aaye to alert kyun nahi bajta?** `increase()` do samples ke beech ka farak hai; pehli sample ke baad hi series ban jati hai to pehli event 0 dikhti hai. Live test me `WhatsAppTokenError` pehli baar chup raha; ab alert wale series 0 se pre-create hote hain.
